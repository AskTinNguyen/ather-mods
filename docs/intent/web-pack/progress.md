## Decisions (worker)

- W1: layouts are compared per `check()` call in run order; any difference in order, text or count is a regression.
- W2: packs live in `ather-automata/hooks/packs/` (one hooks module per plugin, so the engine loads them as relative imports). A pack is a plain object (`Pack` in `packs/index.mjs`); pure functions take it as a last parameter defaulting to `unreal`, so S2 code paths are byte-for-byte the old ones.
- W3: per-person store keys that mean different things per pack are prefixed: the role is `role:<person>` for Unreal (unchanged), `role:web:<person>` for web, `role:core:<person>` for core. Trap counts stay machine-wide, but each pack only offers its own traps as rules (an S2 trap never shows in a web repo, and the reverse).
- W4: the web pack writes lane heartbeats and away ledgers without an intent under `.ather/local/` (S2 keeps `Saved/AtherAutomata/`); debriefs go to `docs/intent/<slug>/debrief.md`. See F-2 for the gitignore line.
- W5: the web rungs are `tests`, `lint` (lint and typecheck: a profile's `typecheck` proof folds onto it), `build`, `ui`, `prod`. Required for Prove: engineer tests + lint + build, designer ui, product build + ui, each cut to what the profile declares. A merge under `with-proof` needs every declared rung except `prod` (production is checked after the merge). Pass needs the tool's own counts or exit 0 (a piped command's exit is the filter's, so only counts decide); a failure count or a non-zero exit fails; an unreadable run records `none`.
- W6: Create in a web repository offers the five Claude Code skills whether or not the repository has a skills folder (`isGlobal`); review skills are run on the current work, the rest start an intent.
- W7 (2026-10-10, replaces "one result per rung" in W5): a gate's result is kept by its `id` (its command when it has none). A rung that gates declare passes when every gate that declares it has passed, fails when one failed, and is otherwise not proven. A gate's run replaces only its own result; several gates in one command each get the reading of the whole command. A script that is no gate but runs gates inside counts for those gates. A command that runs none of the rung's gates (a tool run directly, a script with no gate in it) cannot pass such a rung; a failure it reads fails the rung until one of the rung's gates is next run, or until a later such command reads no failure (the latest one replaces the one before). A result is good for a day, per gate, and a passed rung is as old as its oldest gate result, so D2's "in this session" holds for every gate. A rung that no gate declares, and a repository without a profile, read as before: the latest run replaces the one before. What W5 says a reading needs is unchanged (`tests` and `ui` pass on counts only), so a gate that declares `tests` and prints no counts does not pass when it is run by itself: han-viet's `curriculum` gate is one. Run alone, as Prove asks, it leaves han-viet's `tests` rung unproven until that gate prints counts, leaves `tests`, or W5 changes; in one command with a counted gate (`npm test && npm run curriculum:verify`) it takes that command's reading. (W8 changes this: a gate of the profile passes on its exit code unless its profile entry says `counts`, so han-viet's `curriculum` gate passes when it is run by itself.)
- W8 (2026-10-10, replaces "`tests` and `ui` pass on counts only" in W5 and W7, for a gate of the profile): the profile says how a gate passes. Source: the owner's three instructions on the review of PR 45, given in Vietnamese; this is a reading of them. One, how a run is read differs by repository, because the languages differ (Go, Rust, TS, JS), so it cannot be one rule for all. Two, at setup the agent studies the repository and sets this part up itself. Three, nobody on the old version may get a fault when they update. A gate may carry one optional field, `passOn`, with the value `exit` or `counts`; anything else in the field reads as no field. It says how the gate's `tests` and `ui` proofs pass. With `exit`, an unpiped run that exits 0 passes even when the pack reads no pass counts in it. With `counts`, only the runner's own pass counts pass, as W5 had it. Counts the pack can read still decide first in both: a failure count fails, also piped; a non-zero exit fails; "no tests ran" fails; a pass count passes. A piped run with no counts is not proven, with either value. The exit code counts for this only when it is the gate's own: the gate by itself or after `&&`, not after a pipe, `;` or `||`, and not with another command on a later line. Otherwise the gate is not proven and the session is told to run it by itself. The exit code passes only a gate the command runs itself (a part of the typed command is the gate's command). A gate found inside a script that is no gate still gets that run's result (W7), but it is read on counts, as before, because the script's exit code need not be the gate's. A call that was denied never ran: the web pack reads nothing from it, for every rung, so a refused gate no longer reads as exit 0 (before, it passed `lint` and `build`). A gate without the field reads as `exit`, because of instruction three: a profile written by 0.2.5 or earlier has no field, and since W7 a gate of it on `tests` that prints no counts (han-viet's `curriculum`, or any `go test` or `cargo test`) could never pass, which kept Prove open and held a with-proof merge. The new line is for a gate of the profile only. A command that is no gate (a tool run directly, an npm script with no gate in it), a repository without a profile, and the core pack read as before: no counts, not proven. When one command ran gates of both kinds for one rung, each gate gets the reading of the whole command under its own value. `lint` and `build` are unchanged whatever the field says: they pass on an unpiped exit 0 with no error the pack reads. They keep their older reading of the exit code, which only a pipe into a known filter (`tail`, `grep`, …) hides. `prod` is no gate's proof. Instruction two is not built as a setup step, because the owner removes `/ather setup` from the plugin (decided the same day). Whoever writes the profile, a person or a session, chooses the value from the gate's real output, and the README's Proof bullet says how. Cut on purpose: patterns or regular expressions in the profile, and readers for the counts of `go test`, `cargo test` and `pytest`.
